### Key Architectural Decisions for Your Review

1. **Technology Stack Recommendation: Node.js (TypeScript) + Fastify + PostgreSQL 16 + Redis 7 + React/Vite SPA**
   - **Throughput & Low Latency**: Fastify delivers ~30,000–45,000 req/sec with compiled JSON schemas (`fast-json-stringify`), outperforming Express and FastAPI for high-concurrency event loops.
   - **Shared Type Safety**: Zod DTO schemas are shared between backend endpoints and the React frontend, eliminating contract drift.
   - **Lightweight Footprint**: Alpine-based container images (~140MB) run reliably on a college laptop over Ethernet with minimal CPU/RAM overhead.

2. **Real-Time Architecture: Server-Sent Events (SSE) + Redis Pub/Sub**
   - 99.9% of real-time CTF traffic is server-to-client (solve ticker, score deltas, announcements).
   - SSE uses standard HTTP/1.1 or HTTP/2 streams without the WebSocket protocol upgrade handshake, ensuring reliable connectivity through restrictive campus firewalls, captive portals, and unmanaged switches.
   - Built-in browser reconnection using `Last-Event-ID` handles intermittent Wi-Fi drops automatically.

3. **Concurrency & Scoring Integrity: Financial-Style Immutable Ledger**
   - Flag submissions execute inside atomic PostgreSQL transactions using row-level locking (`SELECT ... FOR UPDATE`).
   - A unique database constraint `UNIQUE(team_id, challenge_id)` on `team_solves` prevents double-scoring or race conditions under simultaneous team submissions.
   - Scores are never modified directly; they are derived from an immutable `score_events` ledger. The primary tie-breaker is strict timestamp ordering (`score DESC, last_score_at ASC`).

4. **Dual-Environment Portability (College LAN vs Production Server)**
   - **Zero Code Changes**: The exact same codebase runs in both environments via environment-driven configuration (`DEPLOYMENT_MODE=lan|prod`) and Docker Compose overlays (`docker-compose.lan.yml` vs `docker-compose.prod.yml`).
   - **Offline-First (LAN)**: Web fonts (`Inter`, `JetBrains Mono`) and icons are self-hosted within the static bundle. Zero external CDN calls are made, ensuring full functionality even if the venue loses internet connectivity.

5. **Challenge Sandboxing & Infrastructure Isolation**
   - Dynamic vulnerable services run on an isolated Docker bridge network (`ctf_challenges_net`) with `cap_drop: ALL`, `read_only: true`, `pids_limit: 100`, and `mem_limit: 128m`.
   - Vulnerable containers have **no network routing** to the core database (`PostgreSQL:5432`) or cache (`Redis:6379`).
   - Static challenge files are served via NGINX `X-Accel-Redirect` after token validation, keeping file buffers out of Node.js memory.

6. **Stage-Gated Roadmap**
   - **Stage 0**: Requirements & Architecture *(Current)*

### Delivered Components in Stage 4:
1. **Capped Component Scoring Model**:
   - `challenges.points` is the maximum obtainable reward for any challenge.
   - Checkpoints award partial points; final flag solve awards `max(0, challenge.points - awardedCheckpoints)`.
   - Score floor enforced at `0` for all penalties.
2. **Immutable Score Ledger & Accounting**:
   - `score_events` tracks all point events (`final_solve`, `checkpoint_solve`, `hint_penalty`, `admin_adjustment`) with running team score snapshots.
   - Diagnostic `reconcileTeamScore` utility ensures `SUM(score_events.points) === teams.score`.
3. **Anti-Tampering Checkpoints Engine**:
   - Multi-step verification enforcing prerequisite chaining (Step N requires Step N-1).
   - Validates `token_proof`, `sub_flag`, and custom tokens in constant time (`timingSafeMatch`).
4. **High-Concurrency Idempotency Guarantees**:
   - Pessimistic row locking with `FOR UPDATE` combined with hard unique database constraints (`UNIQUE(team_id, challenge_id)`, `UNIQUE(team_id, checkpoint_id)`, `UNIQUE(team_id, hint_id)`).
   - 50 concurrent submissions by the same team guarantee exactly 1 reward and 49 duplicate responses without double-scoring.
5. **Rate Limiting**:
   - Sliding-window rate limiter via Redis with in-memory fallback protecting all submission and checkpoint endpoints.
6. **Decoupled Post-Commit Event Boundary**:
   - `scoringEventBus` publishes score events strictly after PostgreSQL transaction commits, preparing for Stage 5 real-time broadcasts.
